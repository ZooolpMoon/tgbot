## 🤖 AI 对话

- 默认模型 `@cf/meta/llama-3.3-70b-instruct-fp8-fast`；主模型报错或返回空内容时按 `llama-3.1-8b-instruct-fast → mistral-7b-instruct-v0.1` 依次回退，全部失败才提示异常（可用 `AI_MODELS` 覆盖整条链）
- 上下文双重限制：最多 **10 条** + 最多 **6000 字符**（`AI_HISTORY_MAX_CHARS` 可调）；超长单条截断到 2000 字符
- **记忆按场景隔离**：私聊一份，每个群的每个成员各一份
- 系统提示词会根据身份（管理员 / 访客）、语言偏好（`/setlang`）、自定义要求（`/setprompt`）与是否群聊动态拼装
- 知识库开启时，回答前会先检索资料并标注来源（见 [知识库](knowledge-base.md)）
- **计费**：每次对话扣 1 积分。顺序是「占今日额度 → 原子扣分 → 调用模型」，任一步失败都会退回已占用的额度与积分
- 频率限制与每日额度按场景配置（默认 5 秒冷却 / 每天 50 条；`-1` 表示不限额度）

### 相关数值

| 项 | 默认值 | 改哪里 |
|----|--------|--------|
| 每次对话消耗 | 1 积分 | `src/config/constants.js` → `POINTS.AI_COST` |
| 新用户初始积分 | 100 | `DEFAULTS.POINTS` |
| 默认每日额度 | 50 条 / 场景 | `DEFAULTS.MAX_DAILY` |
| 默认冷却 | 5 秒 | `DEFAULTS.RATE_LIMIT_SEC` |
| 上下文预算 | 6000 字符 / 10 条 | `RULES.HISTORY_MAX_CHARS`、`RULES.HISTORY_LIMIT` |

单个用户 / 单个群的额度与冷却不需要改代码——在管理后台对应场景里直接调。

## 🪙 积分体系

| 项 | 默认值 |
|----|--------|
| 新用户初始积分 | 100 |
| 每次 AI 对话 | −1 |
| 签到基础奖励 | +5，每连续一天 +1，上限 +20 |
| 连续 7 天里程碑 | 额外 +20 |

积分是**全局共享**的：同一个人在私聊和任何群都用同一份积分；但额度、冷却、AI 记忆、功能开关都是**按场景独立**的。

- `/points` 查看流水（每页 10 条，可翻页），每笔变动都记录变动值、变动后余额、原因与时间
- `/rank` 查看排行榜 Top 10（含自己的名次）
- 管理员可以在用户详情里调整积分（原子更新 + 流水），也可以直接封禁 / 解封
- **积分安全**：扣分用 `UPDATE users SET points = points - ? WHERE points >= ?`（余额不足直接失败，绝不会出现负分）；失败路径会写补偿流水

## 📅 签到

- `/checkin`（别名 `/sign`）按 `APP_TIMEZONE` 判定日期，每天一次
- 连续签到奖励递增；断签后连续天数归零
- 同一天重复签到只提示，不会重复发奖
- 签到奖励按「用户 + 日期」记录，跨私聊与群聊共用；`/profile` 会显示累计与连续天数

## 💸 积分转账

- `/transfer <用户ID|@用户名> <数量>`；也可以**回复对方的消息**后只发 `/transfer 50`
- 单笔范围 `TRANSFER.MIN ~ TRANSFER.MAX`（默认 1 ~ 1000000），必须整数
- 不能转给自己；对方必须用过本机器人（否则没有账户可以接收）
- 扣分用原子条件更新（余额不足直接失败），给对方加分失败会自动退回
- 双方各记一条 `points_log` 流水，方便对账

## 🎁 每日抽奖

- `/lottery` 打开抽奖面板（别名 `/draw`）
- **每天 1 次免费**（靠部分唯一索引保证，不会重复中奖）
- 也可以按次**花积分抽**（`LOTTERY.PAID_COST`，默认 10 分）
- 奖池与权重在 `config/constants.js` 的 `LOTTERY.PRIZES`，**期望值刻意低于单次成本**，避免被当成刷分入口
- 抽奖记录存 `lottery_draws`，每次发奖都写积分流水

## 🛠️ AI 工具调用

让 AI 能**查数据**，而不是只会聊天：

| 工具 | 作用 |
|------|------|
| `get_my_points` | 查提问者自己的积分余额 |
| `get_my_checkin` | 查累计与连续签到天数 |
| `get_rank` | 积分排行榜前 5 名 |
| `get_group_rules` | 当前群的群规（私聊里为空） |
| `search_knowledge` | 在知识库里检索资料（本群优先，其次全局） |

工作方式（v3.0.1 起改为**确定性预取**）：

1. 用关键词识别「用户明显在问哪种数据」——例如「我有多少分」「签到几天了」「看看排行榜」「群规是什么」
2. 直接执行对应查询，把结果以**实时数据**的形式拼进上下文（**提示词里不出现工具名**）
3. 模型只负责用自然语言把数据讲清楚 —— 一次模型调用搞定

> 为什么不交给模型自己决定调哪个工具：实测 llama 系模型不会老实按约定输出 JSON，
> 反而会把工具名当成「指令 / 资料」讲给用户听（例如「请先使用 get_my_points 指令查询」）。
> 预取方案只花一次模型调用，而且任何模型都能答对。

- **只读**：任何会改状态的动作（封禁 / 发积分 / 改配置）都不在工具列表里，仍必须走显式指令 + 确认卡片
- 开关：功能开关里的「AI 工具调用」，可按全局 / 场景关闭

## 🎮 小游戏

入口 `/game`（别名 `/games`）。所有游戏都是「先扣分再开奖」，扣分失败不会开奖。

| 游戏 | 玩法 | 赔率 |
|------|------|------|
| 🎲 骰子猜大小 | 3 个骰子点数和 3-10 为小、11-18 为大 | 1:2（含本金） |
| 🎰 老虎机 | 三个相同 10 倍，💎💎💎 50 倍，任意两个相同 2 倍 | 2x / 10x / 50x |
| 🪙 抛硬币 | 猜正反面，胜率 50% | 1:2（含本金） |
| 🎡 幸运转盘 | 按概率抽倍率 | 0x / 0.5x / 1x / 2x / 5x / 10x / 50x |
| 🃏 21 点 | 跟 AI 庄家对赌，可要牌 / 停牌 / 双倍 | Blackjack 3:2，普通赢 1:1 |
| 🔴⚫ 轮盘赌 | 欧洲轮盘 37 格，押红黑 / 单双 / 大小 / 三打 | 1:1 或 2:1（返还率 97.3%） |

幸运转盘的概率分布（页面内也会显示）：

| 倍率 | 概率 | 结果 |
|------|------|------|
| ×0 | 30% | 失去本金 |
| ×0.5 | 25% | 拿回一半 |
| ×1 | 20% | 保本 |
| ×2 | 15% | 翻倍 |
| ×5 | 8% | 5 倍 |
| ×10 | 1.5% | 10 倍 |
| ×50 | 0.5% | 50 倍大奖 |

玩法细节：

- 每个游戏都有固定下注（10 / 50 / 100）与**自定义下注面板**（±10 / ±100 / 最小 / 全押），金额自动收敛到 `[1, 当前积分]`
- 开奖后可直接「相同金额再来」
- 每局结算都会写积分流水；老虎机与转盘记录的是**净变动**
- 随机数用 `crypto.getRandomValues`（`src/utils/random.js`），不用 `Math.random`

### 🃏 21 点（AI 庄家）

唯一一个**多轮牌局**：下注后不是立刻开奖，而是一轮轮要到满意或停牌为止。

| 规则 | 说明 |
|------|------|
| 牌堆 | 单副 52 张，**每局重新洗牌**；牌堆存在牌局记录里，跨多次点击不会换牌 |
| A 的算法 | 可当 1 或 11，自动取「不爆的最大值」（`A + 6` = 17 软牌，`A + 6 + K` = 17 硬牌） |
| Blackjack | 首两张 21 点，赔 **3:2**（双方都 Blackjack 为平局退本金） |
| 庄家规则 | **不足 17 点必须继续要牌，到 17 点停牌**（软 17 也停） |
| 玩家操作 | 要牌 / 停牌 / 双倍（只在首两张时可用：本金翻倍，只再补一张后自动停牌） |
| 平局 | 退回本金 |

**AI 负责什么**：牌局的每一步判定都走上面的固定规则 —— 公平、可验证、不拖慢节奏。AI 只负责在结算时说一句台词（挑衅 / 打趣 / 认栽），每次结算调用一次模型，**调用失败或超时就用内置台词**，不会因为模型抽风卡住结算。想换模型链，改 `AI_MODELS` 或 `env.AI_MODELS` 即可（取第一项）。

**资金安全**：开局先扣本金，结算时按输赢返还。牌局 **30 分钟**没有动作会被定时任务作废，并**退还本金**（不会因为「没点完」就吞掉用户的积分）；双倍下注用原子条件拦住重复点击，不会重复扣本金。

每个会话一人一局：进行中的牌局会保留，从游戏大厅再进来会**接着打**，不会重复扣分。

### 🔴⚫ 轮盘赌（欧洲轮盘）

37 格（0-36），一次下注一次开奖，是**数学模型自带抽水**的游戏 —— 不需要像老虎机那样自己调权重。

| 下注 | 覆盖 | 赔率 | 命中概率 |
|------|------|------|----------|
| 🔴 红 / ⚫ 黑 | 18 个号 | 1:1 | 18/37 |
| 单数 / 双数 | 18 个号 | 1:1 | 18/37 |
| 小 (1-18) / 大 (19-36) | 18 个号 | 1:1 | 18/37 |
| 1-12 / 13-24 / 25-36 | 12 个号 | 2:1 | 12/37 |

**庄家优势来自「🟢 0 通杀所有外围注」**：37 格里只有 36 格算外围，所以四种下注的返还率都是 `36/37 ≈ 97.3%`。`test/roulette.test.mjs` 里有一条**返还率守卫**——改赔率表时必须重算，否则测试会直接失败（防止不小心把游戏改成刷分渠道）。

- 卡片顶部显示**近 10 期开奖**（全局共享，纯展示），方便看「走势」
- 押中后可以「再押同样的」或「换个押法」，金额默认沿用上一把
- 下注后是**立即开奖**，没有中途操作，所以不需要牌局状态表

> 没做单号 35:1：37 个数字放不进 Telegram 键盘（约定整个菜单 ≤ 8 行、每行 ≤ 2 个按钮），而且 1/37 的中奖率下「点三次选号还没中」的体验很差。想要可以再加分页选号。

## 🛒 积分商城

**仅私聊可用**（群里使用会提示去私聊）。

### 用户侧流程

```
/shop 或 /store
  → 商城首页（商品列表，可翻页；顶部显示「我的背包：N 件未使用」）
  → 商品详情（价格 / 库存 / 限购 / 发放方式 / 说明 / 我的备注）
  → ✍️ 填写备注（可选，30 分钟内有效）
  → ✅ 确认兑换
  → manual：订单为「⏳ 待处理」，管理员收到通知，标记完成后私聊通知你
    bag   ：订单直接完成，物品进「🎒 我的背包」，你自己挑时间用
  → /orders 我的订单：待处理可「❌ 取消并退款」，未使用的背包订单可「↩️ 退款」
  → /bag 我的背包：查看与使用背包里的物品
```

### 订单状态机

```
pending（待处理）─── 管理员标记完成 ───→ done（已完成）─── 退款 ───→ refunded（已退款）
      │                                  │
      │                                  └── 背包物品已使用 → 不可退
      └── 用户自助取消 / 管理员取消 ───→ cancelled（已取消，积分已退、库存已回滚）
```

### 退款（已完成订单）

只有「**背包物品还在背包里没动**」的 `done` 订单能退款——东西能原样收回、库存能回滚，所以可以自助即时到账；已经使用过的物品说明东西已经交付，不能再退（用户与管理员都一样）。

退款链路：`done → refunded`（原子状态流转，只有真正改到状态的那一次才退）→ 收回未使用的背包物品 → 退积分 → 回滚库存（仅有限库存商品）→ 写 `shop_order_log` → 通知用户 + 同步管理员。

`refunded` 与 `cancelled` 一样**不占限购名额**，退过款还能再买。

### 自动发放（`shop_items.delivery`）

商品多了一个**发放方式**字段，决定下单之后由谁把它交付给用户：

| delivery | 行为 |
|----------|------|
| `manual`（默认） | 下单后是「⏳ 待处理」，通知管理员，由管理员标记完成 |
| `group_tag` | 下单**直接完成**、不通知管理员，立刻进入机器人自己的发放流程 |
| `bag` | 下单**直接完成**、不通知管理员，物品自动进「🎒 我的背包」 |

目前内置一件 `group_tag` 商品：**🏷️ 自定义群组标签（500 积分）**。

### 🎒 我的背包

入口：`/bag`（别名 `/backpack` `/items`）或 商城首页 → 「🎒 我的背包」，**仅私聊**。

```
购买 delivery = bag 的商品
  → 订单直接完成，物品进背包（未使用在前，每页 5 件）
  → 点物品下面的「✅ 使用」
       ├── 用法 points：立刻按快照的积分数加分（写积分流水）
       └── 用法 none  ：标记已使用，私聊通知管理员去交付 / 核销
```

物品的**用法配在商品上**，并在**下单时快照**进背包记录——之后改商品配置不影响已经买到的物品：

| `shop_items.use_type` | 行为 |
|-----------------------|------|
| `none`（默认） | 仅核销：用户点「使用」后标记已用，管理员收到私聊通知 |
| `points` | 使用后兑换成 `use_value` 积分（原子加分 + `points_log`） |

管理员在 `/shop_add` 的第 7 步选发放方式，选「进背包」会继续问用法与积分数；`/shop_edit` 里也能改「🚚 改发放方式」「🎒 改背包用法」。使用与退款都是**原子状态流转**：连点「使用」不会重复发奖，退款也只对「从没使用过」的订单生效。

### 🏷️ 自定义群组标签（可选商品）

卖的是 Telegram 的**成员标签**（群成员昵称旁边显示的自称号），流程：

```
购买（500 积分，下单即完成）
  → 选择「机器人所在的任意群」（按钮，一页 10 个）
  → 发送你想要的标签（1~16 字，不支持 emoji；回复 - 清空）
  → 机器人调用 setChatMemberTag 直接设置，群里立刻生效
```

- 前提有两个，缺一个都换群：
  - **机器人在那个群是管理员，并勾选「管理标签」（`can_manage_tags`）权限**；
  - **买家在那个群里得是「普通成员」**——Telegram 的成员标签只对普通成员生效，**群主和管理员都不行**（群主的名字由「管理员头衔」控制，管理员同理；硬试会返回 `CHAT_CREATOR_REQUIRED`）。
- 每个群每个用户只有一个标签，重新购买可以改
- 会话 30 分钟内有效；过期或放弃后可从「📜 我的订单」点「🏷️ 设置标签」重新进入（订单不会作废）
- 用户设置标签属于自助发放，不打扰管理员；机器人只在 `bot_chats` 里缓存群名与权限检查结果（1 小时）

### 关键设计

- **商品快照**：订单保存下单时的名称、图标与价格，之后改价改名不影响历史订单
- **原子扣分**：余额不足直接失败，不会超扣
- **原子取消**：`UPDATE ... SET status='cancelled' WHERE id=? AND status='pending'`，只有真正把状态从 `pending` 改掉的那一次才退款，不会重复退
- **库存不足自动退款**：扣库存失败立即退回积分
- **限购并发兜底**：下单后按真实订单数复核一次，并发点击导致超出的那一单自动取消并退款
- **取消退款链路**：退积分 → 回滚库存（仅有限库存商品）→ 写订单日志 → 通知用户

### 商品分类

| 类别 | 说明 |
|------|------|
| `virtual` 虚拟物品 | 卡密、兑换码、道具等 |
| `service` 服务 | 代做、咨询、定制等 |

商城只保留这两类（早期版本的「实物 / 发货」已移除，历史数据会自动归入虚拟物品）。

## 🎟️ 兑换码

- 格式 `TG` + 8 位，字符集去掉了易混淆的 `I O 0 1`
- 大小写、空格与连字符都能识别（`tg-7kq2-m4xz` 也能用）
- 可设总次数上限（`0` = 不限）与有效天数（`0` = 永久）
- **每个码每人限兑一次**，由数据库唯一约束保证
- 兑换流程：占「每人一次」名额 → 条件更新占全局次数 → 发积分；任一步失败都会补偿回滚
- 管理员可随时停用 / 启用，列表支持分页

```
管理员：/code_new 100            → 100 积分，限 1 次，永久
管理员：/code_new 50 20 7        → 50 积分，限 20 次，7 天有效
用户  ：/redeem TG7KQ2M4XZ
```

## 👋 入群欢迎与验证

新成员进群时自动欢迎，可以顺带要求对方**点一下按钮通过验证**（默认关闭，先用 `/welcome` 开启）。

### 开启方式

在**目标群里**（机器人得是管理员）发 `/welcome`：

```
👋 入群欢迎与验证
-------------------------
🔴 已关闭　·　验证：关闭
⏱ 超时：10 分钟　·　超时处理：移出群聊

[🔛 本群：已关闭]  [🔓 验证：关闭]
[⏱ 超时：10 分钟] [👢 超时移出：是]
[✏️ 编辑欢迎语]    [♻️ 恢复默认]
[❌ 关闭]
```

- **🔛 本群开关**：这是功能开关的**群级**配置。默认关闭 —— 会主动往群里发消息的功能不该在升级后自动生效
- **🔓 验证**：开启后，机器人会先**限制新成员发言**，对方点「✅ 我已阅读群规」才放开
- **⏱ 超时**：5 / 10 / 30 分钟轮换
- **👢 超时移出**：到点还没验证时，移出群聊（先封再解，以后还能重新加入）；关掉则只解除限制
- **✏️ 编辑欢迎语**：引导式输入，支持两个占位符 —— `{name}`（新成员）、`{group}`（群名）；发 `-` 恢复默认

### 欢迎语默认模板

```
👋 欢迎 {name} 加入 {group}！
请先看一遍群规，和大家友好相处～
```

### 行为细节

| 情况 | 机器人的做法 |
|------|------------|
| 功能关闭 | **什么都不做**（不发消息、不加限制） |
| 只欢迎（验证关闭） | 发欢迎语，不碰任何权限 |
| 开了验证 | 限制发言 → 发带「✅ 我已阅读群规」按钮的欢迎语 → 记录待验证 |
| 群主 / 管理员入群 | 只欢迎，**不限制**（Telegram 也不允许限制管理员） |
| 机器人自己没有「封禁用户」权限 | 自动降级为「只欢迎」，不会假装已经限制 |
| 超时未验证 | 按配置移出群聊，或仅解除限制（**不会**留下永久禁言） |
| 通过验证 | 解除限制 + 收起按钮 + 弹一句「✅ 验证通过」 |

### 几个约定

- 收的是 `new_chat_members` 消息，**不需要**改 webhook 的 `allowed_updates`，老部署升级后不用动配置
- 状态流转全部是**带条件的原子更新**：连点验证按钮、或「用户刚好点按钮」与「cron 刚好到点」撞在一起，也只会执行一次
- 验证按钮只认**点击者自己** —— 别人点了不会把你也放行
- 成员名字是用户可控的，进消息前一律转义；欢迎语模板先转义再拼 HTML
- 这属于「用户自助」，**不是** AI 执法：不需要理由校验，也不会写进处置记录

### 需要的前置条件

| 要做的事 | 需要 |
|---------|------|
| 发欢迎语 | 机器人在群里（能发消息） |
| 限制发言 / 踢出 | 机器人在该群是管理员，且有「**封禁用户**」权限 |

## 🧹 自动反垃圾

入口：群里发 `/automod`（**默认关闭**）。它与「群规执法」的分工是：

| | 谁发现问题 | 怎么做 |
|---|---|---|
| 🛡️ 群规执法 | **人** | 管理员用 `/ban` `/mute` 下指令，理由必须校验通过 |
| 🧹 自动反垃圾 | **机器人自己** | 按行为特征先兜一层，默认只删消息 |

### 三条规则

| 规则 | 判定 | 默认 |
|------|------|------|
| 🧹 刷屏 | 同一人 10 秒内超过 6 条；或单条消息超过 1200 字 | 开 |
| ♻️ 重复 | 同一人 60 秒内发同一内容超过 3 次（去空白、不分大小写） | 开 |
| 🔗 新成员 | 入群 30 分钟内发链接或转发消息 | 开 |

「新成员」要靠入群事件判断，所以机器人会记录**收到 `new_chat_members` 的时间**
（与「入群欢迎」开关无关，只留 7 天）；机器人在此之前就已经在群里、或没记录到的老成员，
一律**不**按新成员处理。

### 动作

| 配置 | 行为 |
|------|------|
| 仅删除消息（默认） | 删掉违规消息 + 群里发一条自动删除的提示 |
| 递进禁言 | 第 1 次仍然只删；**第 2 次起**按 10 / 60 / 1440 分钟递进禁言 |

### 三条底线（照抄群规执法的教训）

- **只看行为，不看内容**：不解析聊天语义，也不从自然语言里猜「该不该封」
- **不碰自己人**：群主、本群管理员、机器人管理员 / 执法员一律豁免 ——
  自动禁言一个管理员可能把后台访问权限一起锁掉
- **不越权下重手**：默认只删消息；禁言必须有期限，而且是管理员显式选的

### 成本

- 计数在 Worker 内存里滚动（isolate 级滑动窗口），**只有真正触发动作时才写 D1** ——
  日常聊天不产生任何额外查询或写入
- 配置读取有 30 秒缓存，也不会每条消息查一次库
- 多 isolate 会让计数分片（实际阈值比配置宽松），这是可接受的：反垃圾要拦的是持续刷屏，
  不是精确计费，而所有动作本身都是幂等的

### 需要的前置条件

| 要做的事 | 需要 |
|---------|------|
| 删除消息 | 机器人在群里是管理员，且有「**删除消息**」权限 |
| 递进禁言 | 还要有「**封禁用户**」权限（没有则自动降级为只删除） |

## 📰 每日群报

入口：群里发 `/summary`（**默认关闭**），开关：`/summary on` / `/summary off`。

> ⚠️ 先说清一件事：`chat_history` 存的是**与 AI 的对话**，里面没有群成员之间的聊天。
> 所以想总结「今天群里聊了什么」，就必须另记一份群消息流水 ——
> 这也是它默认关闭的原因：**开启等于管理员同意记录群成员发言**。

### 记录什么

| 记 | 不记 |
|----|------|
| 文本消息的前 300 字、发送者昵称、时间 | 图片 / 语音 / 视频 / 文件 / 贴纸 |
| 保留最近 **7 天**（每天自动清理） | 指令消息（`/` 开头）与机器人自己的发言 |

### 群报长什么样

```
📰 群报 · 2026-09-18
-------------------------
💬 消息 123 条 · 👥 活跃 15 人

今天主要在聊新版本的功能取舍，重点讨论了抽奖的赔率和群报的隐私边界。
· 有人反馈商城加载慢
· 讨论了下周的活动安排
❓ 待回应：抽奖能不能设置成只允许老成员参加

🔥 发言最多：小明(20) 小红(12) 阿伟(8)

👋 新成员 1 人 · 🧹 自动处置 2 次
```

### 怎么生成的

- **统计**（消息量 / 活跃人数 / 发言排行 / 新成员 / 自动处置次数）走 SQL 直接算，不花模型调用
- **摘要**才调一次模型，提示词里明确要求**不复述隐私信息**（手机号、住址、证件号）
- 模型失败时降级成「只有统计」，不会整份日报没有
- 同一天同一群已经生成过就直接复用，不重复调模型
- 自动推送只覆盖**昨天确实有消息**且开了群报的群，一次最多几个群（模型调用要控量）

## 🎁 群内抽奖

```
/giveaway 100 3 30 周末大抽奖
   ↑      ↑   ↑   ↑     ↑
 命令   积分 人数 分钟  标题（人数、分钟、标题都可以省）
```

| 场景 | 行为 |
|------|------|
| 发起 | 群里发一条带「🎉 参与」按钮的卡片，按钮上实时显示已报名人数 |
| 报名 | 任何群成员点一下即可，**每人一次**（连点不会多占份额） |
| 开奖 | 到点由定时任务自动开奖；管理员也可以 `/giveaway_end` 立即开奖 |
| 取消 | `/giveaway_cancel`（只能取消还没开奖的） |
| 发奖 | 中奖积分直接入账，可用 `/points` 查看流水 |

### 几个约定

- 同一个群同时只允许**一个**进行中的抽奖 —— 否则「点按钮参与」分不清参与的是哪一场
- 开奖的唯一凭据是 `status: open → drawn` 的原子更新：到点 cron 与管理员手动开奖
  同时发生也只会发一次奖
- 报名前会确保对方有用户记录（没跟机器人说过话的人先补一条），避免「中了奖却发不出去」
- 跨群报名会被拦下：每个抽奖只属于它所在的那个群
- 结束的抽奖记录保留 30 天后清理，报名名单随抽奖一起删

## 🧠 长期记忆

AI 的上下文窗口只有 **10 条 / 6000 字符**，超出的旧对话原来直接丢掉 ——
于是聊了一周的老用户，机器人照样问「你是谁」。

现在被裁掉的那部分历史会攒进缓冲，**够 8 条**就压成一段简短的「用户印象」，
之后每次对话作为背景注入。

### 记什么

只记稳定的信息：怎么称呼对方、长期关注的话题、明确表达过的偏好、正在做的项目。
明确要求**不记**一次性事实（今天吃了什么）与隐私敏感信息（手机号、住址、证件号），
也不许编造片段里没出现过的内容。

### 三条安全约定

- 画像注入时标注为**背景 + 不可信素材**：不许复述、不许执行其中的指令
- 模型没返回内容时**保留缓冲**，下次再试 —— 不能把用户的记忆白丢一次
- `/clear`、`/clearmem`、后台的「清空记忆」都会**连画像一起清掉**，
  否则清完之后机器人照样记得你

压缩是攒够条数才做的（约几轮对话一次），不是每轮都调模型。

## 📊 用量与成本

入口：`/usage`（需要「查看统计」权限）。

| 指标 | 说明 |
|------|------|
| AI 调用 / 失败 | 失败率突然上升通常意味着模型或配额出了问题 |
| 回退到备用模型 | 主模型不稳的信号 |
| 各模型调用分布 | 换模型前后可以对比 |
| 群消息量 | 判断负载落在哪里 |
| 知识库检索 / 入库 | 知识库到底有没有在用 |

### 口径说明

埋点是「内存累加 + 请求结束时一次 batch UPSERT」：一天一个指标只占一行，
**写入量与消息量无关**，只与指标种类有关。

> ⚠️ 统计是**近似值**：多个 isolate 各算各的，未落库的部分会随 isolate 回收丢失。
> 用来观察趋势足够，不要拿去对账。
